# Origin keys and reconnect behavior

This is the gateway-to-client HMAC transport contract, not Google user authentication, backend Service Auth, a Tunnel token or a provider-management credential. Each credential has a different holder and revocation procedure. Actual account-specific installation, deployment propagation and revocation must be qualified before live activation.

## Private key-set binding

New installations use the **secret** binding `YOLO_GATEWAY_KEYS` at the client Worker and operator gateway. Its value is a JSON object with exactly `version: 1`, `current` (a fresh random 32-byte key encoded as 64 lowercase hex characters), and optionally `previous`. The latter has exactly `secret` (a different 64-hex key), `notBefore` and `notAfter` (integer Unix seconds). Its interval is `[notBefore, notAfter)` and must last at most **900 seconds**. This is our transport ceiling, not a provider allowance. Keep clocks accurate; previous-key expiry has no grace beyond the specified instant.

The signer always uses `current`. The verifier accepts that key, or the previous key only inside its interval. App origin, method, path/query and timestamp remain signed using the v1 wire format; TLS protects the request body. Requests are not a nonce/replay database. A present but invalid/empty key-set binding fails closed and never falls back. Only an **absent** key-set binding allows legacy `YOLO_GATEWAY_SECRET` for compatibility with older local previews/installations. Once migrated, delete the legacy secret from both current configurations and keep the key-set binding present during suspension and recovery. Removing it while a legacy key remains would re-enable that key.

Use owner-controlled private secret storage outside Git and browser/build environments. Generate/store the JSON there; do not paste values in source, issues, chat, shell arguments or logs. Record only secret names, version identities, cutoff times and nonsecret acceptance results. Only verified authorized owners receive their app's runtime key; neither side gives provider-management credentials to the other. Same-owner setup can use existing private owner storage. Independent-owner recipient verification/encrypted delivery must be agreed and exercised before use; this guide does not create a secret relay or prove that qualification.

Before each installation/rotation, follow the current official [secret](https://developers.cloudflare.com/workers/configuration/secrets/), [deployment](https://developers.cloudflare.com/workers/versions-and-deployments/) and [rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) references. Check whether the selected operation changes a version, traffic, secrets or old-version availability; do not assume a secret update is inert or universally shared across versions. Bind private evidence to both actual accounts/Workers, code versions and bindings. If current behavior, authority or compatibility is unknown, stop the provider action. No live operation is authorized by this document.

## Routine replacement

1. Verify the existing client and gateway code understand this key-set contract. For an older scaffold, compare the identified new bundle with client-owned files and deliberately merge `transport.mjs`/`worker.mjs` and integration changes under that client's authority. Instantiation preserves conflicts; it is not an automatic file upgrader. Keep existing app code/assets/configuration. Prove the guard on all direct/preview/version/API paths before changing a live key.
2. Privately prepare a new key. Install a **client** key set with the new `current` and old `previous`, with an explicitly agreed cutoff no more than 15 minutes from the start. The old gateway still signs with the previous key. Verify the deployed client version accepts both signed keys and rejects unsigned/forged requests. Do not extend the cutoff to hide a failed rollout; fence and reconcile instead.
3. Install the new current-only key set at the **operator gateway**. Verify actual authorized frontend/API traffic uses the new key, with no automatic retry using the old one. Record the deployed versions in both accounts. No client code/build runs with operator administrative credentials.
4. Remove `previous` from the client binding after the new path is verified (or let it expire at the agreed cutoff). Prove the old key is rejected for assets, version, API, SSE and WebSocket reconnection, and the new key still works. Remove any legacy binding. Verify retired versions/alternate routes cannot bypass this decision. Keep nonsecret results; live propagation and already-running older instances require actual provider evidence.

A failure pauses the rotation for reconciliation. Recover with a compatible code version **and current authorized bindings**; do not restore retired keys, extend overlap automatically or assume old Worker versions inherit new secrets. This sequence supports bounded overlap in the new runtime, not a zero-downtime provider guarantee.

## Compromise, suspension and other credentials

Compromise has **no overlap**. Fence public admission and the client machine endpoint using verified provider controls, retire unsafe versions/routes and terminate active connections as required. Replace with a fresh current-only key set at both authorized runtimes. Prove old-key denial and new-key authorization before restoring routing. An invalid present key set makes this runtime unavailable, but changing one deployment alone does not prove other deployed versions/connections have stopped. Keep recovery artifacts separately from credentials; a code rollback never authorizes reviving a revoked capability.

Origin-key replacement does not revoke Google sessions, backend credentials, connectors, a broker account or the client's background feed. The operator/client owners separately follow the current [Access session](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/), [Service Auth token](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/) and [Tunnel permission/rotation](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/remote-tunnel-permissions/) references, with actual allowed/denied/reconnect evidence. These procedures are not automated or qualified by this scaffold. Do not weaken lifecycle guards or reuse the preparation-only infrastructure tool to force a deletion/update it refuses.

## Application connections

The client bounds upstream headers, response streams and WebSockets to **at most 60 seconds from the signed timestamp**, also capped at 60 seconds from admission. A previous-key request ends earlier at its key cutoff. The operator may impose a shorter window or JWT expiry. Expect normal closes/cancellations and 504 for a deadline before headers; a connection can end sooner for other reasons. Expiry prevents a fresh request with the old key and bounds streams admitted by this code. New configuration cannot retroactively rewrite older running code; live suspension/revocation remains a separate provider operation.

The browser app must reconnect SSE/WebSockets deliberately, with backoff/jitter and a bounded retry rate. Mark disconnected data immediately and track market-feed freshness separately from connection health; never silently show a stale price as live. Use event cursors/`Last-Event-ID` only if the application defines replay/resumption; otherwise refetch a snapshot and reconcile before showing live state. Stop retry loops on authorization denial and require reauthentication through the public origin. A network close is not proof that the user logged out. Do not automatically replay a state-changing request or paper order without the app's idempotency/reconciliation contract. Continuous backend ingestion must remain independent of browser connections.

Local synthetic HMAC/workerd checks establish this runtime contract, not real Google revocation, provider propagation, cross-account free-tier compatibility, market-data licensing or paper-engine correctness.
